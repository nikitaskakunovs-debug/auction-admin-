# 12 · Нумерация лотов, заказов и что из неё утекает

Утверждено 17.08.2026.

Две цели, которые обычно противоречат друг другу:

1. Сотрудник читает номер и сразу понимает, что это за вещь и куда её нести.
2. Конкурент, купивший два лота с интервалом в месяц, **не** может вычесть один
   номер из другого и узнать наш оборот.

Второе достигается ровно одним способом: **в номере не должно быть
последовательности**. Всё остальное — детали.

---

## 1. Что есть сейчас и что оно выдаёт

| Что | Формат | Где задаётся | Утечка |
|---|---|---|---|
| Артикул лота | `LOT-000123` | `packages/domain/src/intake.ts:10` | **Полный приход.** Два лота — и виден весь объём закупки между ними |
| Номер заказа | `A-1028` | `apps/api/src/engine/close.ts:90`, `purchase.ts:78` | **Полный объём продаж.** Счётчик без пропусков |
| Поставка | `CON-0042` | `intake.ts:16` | Объём поставок, но клиенту не показывается |
| Счёт | `{серия}-00001` | `apps/api/src/engine/invoices.ts:75` | Объём — **и убрать нельзя, см. §6** |
| Номер на табло | 100–999, сброс в сутки | `packages/db/src/schema.ts:652` | Дневной поток. Его и так видно, стоя в зале |

`A-1028` — самая дорогая утечка. Покупает конкурент лот сегодня и лот через
месяц, вычитает, делит на 30 — получает наши заказы в день. Бесплатно и точно.

## 2. Новый формат лота: `66-K7Q4C`

```
6 6 - K 7 Q 4 C
│ │   └─┬───┘ └── контрольный знак (Crockford mod-37)
│ │     └─────── 4 знака Crockford Base32, из CSPRNG
│ └───────────── последняя цифра года прихода (2026 → 6)
└─────────────── складская группа 1–9
```

- 7 знаков без дефиса — влезает в этикетку, в Code-128 и в разговор по телефону.
- 32⁴ = **1 048 576** кодов на группу-год. При 20 000 лотов в год заполнение
  группы — меньше 2 %, вероятность коллизии при генерации ничтожна, и она всё
  равно проверяется уникальным индексом с повтором.
- Соседние по времени лоты: `66-K7Q4C`, `66-3PW9T`, `66-B82HN`. Порядок прихода
  из номеров не восстанавливается.

**Crockford Base32** (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`) — без `I`, `L`, `O`,
`U`. Ноль и «O», единица и «I» не путаются, а `U` выброшен, чтобы алфавит не
складывал случайных грубостей. При вводе `I`/`l` читаются как `1`, `O` как `0` —
кладовщик может ошибиться регистром или буквой, и всё равно попадёт.

**Контрольный знак** — не украшение. На складе номер набирают руками; без
проверки одна опечатка выдаёт **другой существующий лот**, и вещь уходит не тому
человеку. С проверкой опечатка отбивается сразу.

### Складские группы 1–9

Двенадцать категорий движка сворачиваются в девять групп. Группируем **по месту
хранения**, а не по маркетингу — номер нужен кладовщику.

| Группа | Категории движка | Почему вместе |
|:-:|---|---|
| **1** | `electronics` | Отдельная зона, антистатика |
| **2** | `appliances` | Крупногабарит, паллеты |
| **3** | `tools` | Крупногабарит, аккумуляторы отдельно |
| **4** | `furniture` | Паллеты, два человека на подъём |
| **5** | `home_garden` | Обычные полки |
| **6** | `jewellery_watches` | **Сейф.** Отдельный доступ и учёт |
| **7** | `art_antiques` | **Сейф / климат.** Отдельный доступ |
| **8** | `sports_outdoors`, `kids_toys`, `fashion` | Обычные полки, мягкий товар |
| **9** | `food_household`, `other` | Сроки годности, разное |

Группы 6 и 7 получили собственные цифры не для красоты: у них другой доступ,
другая инвентаризация и другая страховка. Кладовщик видит `6` и знает, что идти
в сейф, не открывая карточку.

Соответствие категория → группа лежит в `packages/domain/src/numbering.ts` и
покрывается тестом: каждая из 12 категорий обязана иметь группу, иначе сборка
падает. Категорию у лота менять можно, **номер при этом не меняется** — номер
выдаётся один раз и живёт с вещью до конца.

## 3. Новый формат заказа: `26-8F3KQ`

```
2 6 - 8 F 3 K Q
│ │   └─┬──┘ └── контрольный знак
│ │     └─────── 4 знака Crockford Base32
└─┴───────────── год (2026)
```

Категории в заказе нет: в заказе может оказаться что угодно, а группа уже есть в
номере лота. Год оставлен — по нему сотрудник поддержки сразу понимает, какой
это сезон, и в какой архив смотреть.

**Старые номера продолжают работать.** Поиск идёт по точному совпадению, так что
`A-1028` из старого письма находится как раньше. Ровно та же логика, что уже
описана в комментарии к `generatePickupCode` (`pickup.ts:50-56`) — мигрировать
ничего не нужно.

## 4. Как генерируется

```ts
// packages/domain/src/numbering.ts
const ALPHABET = "0123456789ABCDEFGHJKMNPQRSTVWXYZ"; // Crockford, без I L O U

export function formatLotNo(group: number, year: number, rand: string): string
export function formatOrderRef(year: number, rand: string): string
export function checkChar(body: string): string        // mod 37
export function isValidLotNo(s: string): boolean       // сверяет контрольный знак
export function normalise(s: string): string           // I,l→1  O,o→0  верхний регистр
export function groupForCategory(cat: CategoryCode): number
```

Правила:

- Случайная часть — **`crypto.randomInt`**, не `Math.random`. `Math.random`
  предсказуем, и по одному номеру можно вычислить следующие.
- Уникальность — уникальный индекс в БД плюс повтор до 25 попыток, как в
  `generatePickupCode`. Не «надеемся, что не совпадёт».
- Генерация живёт в `packages/domain`, потому что формат нужен и API, и админке,
  и печати этикеток. Одно место, один тест.
- Нормализация применяется **на каждом входе**: поиск в админке, киоск, скан,
  ввод на стойке.

## 5. Что показываем где

| Место | Показываем |
|---|---|
| Этикетка на вещи | `66-K7Q4C` + Code-128 того же значения |
| Карточка лота в каталоге | `66-K7Q4C` мелким шрифтом рядом с таймером |
| Список выдачи | группа крупно, потом код — сортировка по группе даёт маршрут по складу |
| Заказ у клиента | `26-8F3KQ` |
| Счёт | номер счёта (сквозной, см. §6) **и** номер заказа |
| Табло в зале | только номер талона, ничего больше |

## 6. Что всё равно утекает — и с чем ничего не сделать

**Номер счёта останется сквозным.** Закон о НДС требует, чтобы номера счетов
шли в последовательности без пропусков. Конкурент, купивший два лота с
интервалом, увидит по счетам количество выписанных счетов между покупками.

Уменьшить, но не убрать:

- отдельная серия на год и на рынок (`LV-26-00001`) — тогда номер выдаёт объём
  только этого рынка за этот год, а не весь бизнес;
- счёт отдавать по запросу, а не прикладывать ко всем письмам подряд.

Прятать это дальше нельзя: подделка последовательности счетов — уже не
конкурентная защита, а нарушение.

**Номер талона** 100–999 со сбросом в сутки выдаёт дневной поток. Оставляем:
любой, кто зашёл в зал, посчитает людей глазами, а сотрудникам номер нужен
короткий и произносимый вслух.

## 7. Дефект, который вылезет при оплате на месте

`generatePickupCode` (`pickup.ts:62-68`) проверяет уникальность кода **только
среди заказов со статусом `paid`**:

```ts
.where(and(eq(orders.pickupCode, code), eq(orders.status, "paid")))
```

При оплате на месте код выдаётся, когда заказ ещё `awaiting_payment` — значит
проверка его не увидит, и два человека могут прийти с одним кодом. Условие
обязано стать:

```ts
.where(and(eq(orders.pickupCode, code),
  inArray(orders.status, ["paid", "awaiting_payment"])))
```

Иначе оплата на месте ломает выдачу.

## 8. Порядок внедрения

1. `packages/domain/src/numbering.ts` + тесты (алфавит, контрольный знак,
   нормализация, все 12 категорий имеют группу).
2. Миграция: `items.lot_no`, `orders.ref_new` — оба с уникальным индексом.
   Старые `sku` и `ref` не трогаем.
3. Новые лоты и заказы получают новый номер; старые живут со старым.
4. Поиск в админке, на стойке и в киоске ищет по обоим полям с нормализацией.
5. Этикетки печатают новый номер; напечатанные старые остаются действительными.
6. Счётчики `counters` для `sku` и `ref` остаются — как внутренний
   последовательный id для бухгалтерии, наружу не выходят.
